# hexo-offline

[![Coverage Status](https://img.shields.io/coveralls/JLHwung/hexo-offline.svg?style=flat-square)](https://coveralls.io/github/JLHwung/hexo-offline)

hexo-offline is intended to provide [offline experience](https://web.dev/explore/progressive-web-apps) for [hexo](https://hexo.io) built static website. It uses _ServiceWorker_ under the hood. Simply install this plugin to your website and it should be offline ready by caching most of static assets.

See [here](https://github.com/JLHwung/hexo-offline/tree/v1) for v1 docs.

## Demo

- [徑庭](https://jhuang.me)

## Install

```bash
npm i hexo-offline
```

Once installed, run `hexo clean && hexo generate` to activate offline experience.

hexo-offline requires Hexo 5, 6, 7 or 8 and Node.js ^20.17.0 or >=22.5.0.

## Usage

If the website serves all content from the origin server, you don't have to add any config. Simply install and run `hexo clean && hexo generate`.

While hexo-offline aims to provide zero-config offline enhancement to your hexo project, it does offer full list of options control from [workbox-build](https://developer.chrome.com/docs/workbox/reference/workbox-build#type-GenerateSWOptions). Create a `hexo-offline.config.cjs` in the hexo root directory

```js
// offline config passed to workbox-build.
module.exports = {
  globPatterns: ["**/*.{js,html,css,png,jpg,gif,svg,eot,ttf,woff}"],
};
```

Again, the config is demo only and you don't have to copy and paste if you serve all contents from the origin server.

`globPatterns` and the other glob options are matched against the files Hexo generates, relative to the public folder. The service worker is always generated as `service-worker.js` in the public folder, so `globDirectory` and `swDest` are not supported.

### How it works

hexo-offline runs when Hexo generates the site, after every page has been rendered and before the files are written to the public folder. It adds `service-worker.js` and the Workbox runtime to the generated files and injects the register script into `index.html`, so they are written and deployed like any other generated file, including with `hexo generate --deploy`.

The service worker is generated whenever the site is generated for publishing: `hexo generate`, `hexo generate --deploy`, `hexo deploy --generate`, or a plain `hexo deploy` when there is no public folder yet. A plain `hexo deploy` with an existing public folder deploys it as it is. The service worker is not generated by `hexo server` or `hexo generate --watch` (or while Hexo watches for changes through its API), so local previews don't install one. Because `hexo generate --watch` writes the public folder without the service worker (and removes one generated earlier), run `hexo generate` again before deploying.

To try the service worker locally, run `hexo generate` and serve the public folder on a different port from the one you use for `hexo server`, for example `hexo server --static --port 4001`. A service worker installed on a port keeps serving its cached pages there until it is unregistered in the browser's developer tools.

### Upgrading from v4

- `globDirectory` and `swDest` are no longer supported and are ignored with a warning. Remove them from `hexo-offline.config.cjs`.
- The service worker is now generated together with the rest of the site, so `hexo generate --deploy` and `hexo deploy --generate` deploy it. You no longer need to run `hexo generate` and `hexo deploy` separately.
- `hexo server` and `hexo generate --watch` no longer generate a service worker.
- `skipWaiting` and `clientsClaim` now default to `true`. See [Updating to new content](#updating-to-new-content).
- Node.js ^20.17.0 or >=22.5.0 is required.
- Run `hexo clean` once after upgrading, so the files v4 wrote directly to the public folder (such as an old `workbox-*.js`) are removed.

### Updating to new content

By default hexo-offline sets `skipWaiting: true` and `clientsClaim: true`, so a newly deployed service worker takes over as soon as it is installed. After you deploy, the first page view may still show the cached content. The new service worker downloads the updated files in the background, and once it has finished installing, the next refresh or visit shows the new content.

A page that is already open when the new service worker takes over keeps its old HTML, but any files it requests afterwards come from the new version. If a deploy renames or significantly changes theme scripts or styles, such a page may look or behave oddly until it is reloaded.

To keep Workbox's default behaviour, where a new service worker waits until every tab of the site is closed, set both options to `false` in `hexo-offline.config.cjs`. If the file already exists, add them to the object it already exports rather than adding a second `module.exports`:

```js
module.exports = {
  skipWaiting: false,
  clientsClaim: false,
};
```

### What if content is served via CDN?

Suppose that you have used two CDN scripts:

```yaml
- https://cdn.example.com/script-name/script-version.js
- https://cdn.another-example.org/script-name/script-version.css
```

Add this config to root `hexo-offline.config.cjs`

```js
// offline config passed to workbox-build.
module.exports = {
  runtimeCaching: [
    {
      urlPattern: /^https:\/\/cdn\.example\.com\/.*/,
      handler: "CacheFirst",
    },
    {
      urlPattern: /^https:\/\/cdn\.another-example\.org\/.*/,
      handler: "CacheFirst",
    },
  ],
};
```

For more information, see [Workbox `RuntimeCaching`](https://developer.chrome.com/docs/workbox/reference/workbox-build#type-RuntimeCaching).

Note:

1. As the CDN resources are runtime cached, a resource is cached only after a user agent visits a page that references it. Therefore, if you have included a CDN resource `example.com/script.js` in `some-page.html` only, a user who visits only `index.html` would not have `example.com/script.js` in cache.
1. We use the `CacheFirst` handler because CDN resources with a specific version are not supposed to change in the future.
